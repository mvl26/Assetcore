Single source of truth for project-wide rules. Every skill in `.claude/skills/` should reference this file when the rule applies.

Last updated: 2026-05-11 (Wave 2 status corrections + BE-FE naming contract + fixture 3-list rule + `_parse_json`/`_handle` pattern enforcement).

## 1. Naming Conventions

### DocType naming (CRITICAL — enforce on all new DocTypes)

| Prefix | Meaning | Examples |
|---|---|---|
| `AC ` | AssetCore-owned core entity (replaces ERPNext) | `AC Asset`, `AC Supplier`, `AC Warehouse` |
| `IMM ` | IMM module governance / reference data | `IMM SLA Policy`, `IMM Audit Trail`, `IMM CAPA Record`, `IMM Compliance Rule` |
| (no prefix) | Operational records (legacy Wave 1 — DO NOT extend pattern) | `Asset Repair`, `Asset Commissioning`, `Incident Report` |

⚠️ **Wave 1 broke the rule** with `asset_commissioning`, `asset_repair`. New DocTypes (Wave 2/3) MUST use `IMM ` prefix or `AC ` prefix. Never extend the unprefixed pattern.

### Folder naming
- DocType folder = `snake_case(name)`: `IMM Spare Allocation` → `imm_spare_allocation/`
- Always lowercase + underscores
- 4 files per folder: `__init__.py`, `<name>.json`, `<name>.py`, `<name>.js`

### Workflow state names
- States in workflow JSON use Title Case with spaces: `"Clinical Release"`, `"In Progress"`, `"Pending Verification"`
- DO NOT use underscores in state names. (Tech debt: IMM-04 currently has `Clinical_Release` mismatch — fix when touched.)
- Service code constants must match exactly: `class WorkflowStatus: CLINICAL_RELEASE = "Clinical Release"`

### Service function naming (schedulers)
- Periodic checks: `check_X()` — e.g., `check_capa_overdue`, `check_repair_sla_breach`
- Auto-actions: `auto_Y()` — e.g., `auto_expire_competencies`
- Never use `_` prefix for functions called from `hooks.py.scheduler_events` — they must be public.

### Fixture filename pattern
- `immXX_custom_fields.json` for Custom Fields per module
- `immXX_<thing>.json` for module-specific fixtures (e.g., `imm00_custom_fields.json`)
- One file per module + custom fields scope

## 1b. Fixture Wiring (MANDATORY — 3-list rule)

Every time a workflow is added or modified, `hooks.py` MUST update **all three** lists in the same commit:

```python
# assetcore/hooks.py — update all 3 whenever adding/changing a workflow
fixtures = [
    {"dt": "Workflow", "filters": [["name", "in", [
        "IMM-09 Repair Workflow",
        "<new-workflow-name>",   # ADD HERE
    ]]]},
    {"dt": "Workflow State", "filters": [["name", "in", [
        "Open", "Assigned", "In Repair", "Completed", "Cancelled",
        "<new-state-1>", "<new-state-2>",  # ADD ALL STATES FROM NEW WORKFLOW
    ]]]},
    {"dt": "Workflow Action Master", "filters": [["name", "in", [
        "Phân công KTV", "Bắt đầu sửa chữa", "Hoàn thành",
        "<new-action-1>",  # ADD ALL ACTIONS FROM NEW WORKFLOW
    ]]]},
]
```

**Rules:**
- Missing any one list → fresh-site provisioning fails (workflow exists but states/actions missing from fixtures → `bench migrate` cannot load workflow).
- Fixture file names (`assetcore/fixtures/`) are auto-generated by `bench export-fixtures` — do NOT manually name them. The `hooks.py` `filters` control what gets exported.
- After updating hooks.py: `bench --site miyano export-fixtures --app assetcore` → verify new JSON files created → commit both hooks.py + fixture JSONs.
- Checklist before committing any new workflow:
  - [ ] `hooks.py` Workflow list updated
  - [ ] `hooks.py` Workflow State list has all states from new workflow JSON
  - [ ] `hooks.py` Workflow Action Master list has all action labels from new workflow JSON
  - [ ] `bench export-fixtures` run and new JSONs committed
  - [ ] `tests/test_workflows.py::EXPECTED_WORKFLOWS` updated with new entry

## 2. Architecture Layers (3-tier strict)

```
api/imm<XX>.py          ← thin wrapper, no business logic
   ↓ calls
services/imm<XX>.py     ← all business rules, validators, orchestration
   ↓ calls
repositories/<x>_repo.py ← all frappe.db access (subclass BaseRepository)
   ↓ uses
DocType controllers      ← delegate to service via lazy import; no inline logic
```

### Layer rules (enforce)

| Layer | Allowed | Forbidden |
|---|---|---|
| Controller (.py) | Lazy-import services; call `validate_X(self)` etc. | Business logic, raw `frappe.db.*`, validation throws |
| Service | Validators, orchestration, status transitions, audit logs | Direct `frappe.db.sql()` for CRUD (use repos); HTTP/JSON parsing |
| Repository | All `frappe.get_all/get_doc/db.set_value` calls | Business rules, role checks |
| API | `@frappe.whitelist`, JSON parsing, `_handle()` wrap | Multi-step orchestration, status mutations directly |

### Anti-patterns to flag
- 🚫 `frappe.db.set_value()` inside a service function (use `repo.set_values()` instead)
- 🚫 Business logic in DocType controller (must be `validate_X(self)` delegation only)
- 🚫 `_normalize_filters` defined locally in services — IMPORT from `services.shared`
- 🚫 `_parse_json` redefined per API file — COPY from `assetcore/api/imm09.py` (lines 17–27), the canonical implementation. Existing duplicates are tech debt; do NOT add new ones. New API files must use the same 4-arg signature `(raw, *, field_name, default=None)`
- 🚫 Inline status string `"Open"` instead of `Status.OPEN`
- 🚫 Service function names exposed via API không khớp spec: e.g., tạo `list_training_programs` thay vì `list_programs` như `05_API_Specification.md` quy định. Function name trong `api/immXX.py` phải map 1:1 với spec.
- 🚫 DocType JSON thiếu field nhưng service code tham chiếu `doc.<field>`: trước khi viết service, phải grep tất cả `doc.<field>` và verify từng field trong JSON schema. Lỗi này chỉ phát hiện ở runtime.

## 3. Error Handling Standard

### ServiceError + ErrorCode (canonical)
```python
from assetcore.services.shared import ErrorCode, ServiceError
raise ServiceError(ErrorCode.VALIDATION, "VR-09-03: Mã lỗi tiếng Việt cho user")
```

ErrorCode enum lives in `assetcore/services/shared/constants.py`. Adding a new code requires:
1. Add constant to `ErrorCode` class
2. Document in `.claude/skills/assetcore-be/references/error-codes.md`
3. Update FE `frontend/src/api/errors.ts` mirror

⚠️ **Do not** create a new ErrorCode if an existing one fits. Common: `NOT_FOUND`, `FORBIDDEN`, `VALIDATION`, `BUSINESS_RULE`, `BAD_STATE`, `DUPLICATE`, `INVALID_PARAMS`, `UNAUTHORIZED`, `INTERNAL`.

### API envelope (canonical — IMM-09 is reference)
```json
{"success": true,  "data": {...}}             // success
{"success": false, "error": "...", "code": "VALIDATION"}  // error
```

### `_handle()` + `_parse_json()` pattern (mandatory for new API files)

Every `api/immXX.py` must use this pattern:

```python
# Copy these 2 helpers from imm09.py — DO NOT redefine with different signatures
import json
from assetcore.utils.helpers import _err, _ok
from assetcore.services.shared import ErrorCode, ServiceError

def _parse_json(raw: str | list | dict | None, *, field_name: str, default=None):
    if raw is None:
        return default
    if isinstance(raw, (list, dict)):
        return raw
    try:
        return json.loads(raw)
    except (json.JSONDecodeError, TypeError) as exc:
        raise ServiceError(ErrorCode.INVALID_PARAMS, f"{field_name}: JSON không hợp lệ") from exc

def _handle(fn, *args, **kwargs) -> dict:
    try:
        return _ok(fn(*args, **kwargs))
    except ServiceError as e:
        return _err(e.message, e.code)
```

**Rules:**
- `_handle()` wraps every service call in an API endpoint — never expose raw exceptions.
- `_parse_json()` validates every JSON string param before passing to service.
- Do NOT import `_handle` or `_parse_json` from another API file — copy the block above. They're small, stable helpers. The real consolidation target (`api/utils.py`) is Wave 3 tech debt.
- Existing per-file duplicates (imm01, imm02, imm03, imm04, imm05, imm08, imm15, imm16) are tech debt — do not add new ones.

## 4. Audit & Lifecycle (MANDATORY)

Every business action that mutates an asset state MUST emit:

1. **`IMM Audit Trail`** row via `assetcore.utils.lifecycle.log_audit_event(...)` — SHA-256 chained, tamper-evident.
2. **`Asset Lifecycle Event`** (optional but recommended) — for FE timeline display.
3. **Status transition** via `transition_asset_status(asset, target_status, root_record=...)` from `services.imm00`.

### Hooks where audit MUST fire
- `on_submit` for finalization (e.g., Asset Repair complete)
- `on_update_after_submit` for state changes inside docstatus=1
- Service-level state transitions (e.g., `service.signoff_competency()`)

### Forbidden
- 🚫 Writing directly to `tabIMM Audit Trail` (breaks hash chain)
- 🚫 Skipping audit because "this is a small change" — every state change is auditable per CLAUDE.md §19

## 5. Permissions Model

### Layer 1: DocPerm (JSON / setup_permissions.py)
- Role × Permission Type matrix (read/write/create/submit/cancel/delete)
- Always include: `IMM System Admin` (full access) + at least 2 operational roles
- ❌ Never grant `System Manager` to non-admin DocTypes

### Layer 2: permission_query_conditions (row-level)
- Owner-scoped queries (e.g., technician sees only own work orders)
- Vendor isolation (vendor sees only own assets/contracts)
- Defined in `assetcore/permissions.py`, registered in `hooks.py`

### Layer 3: Service-level role check
```python
from assetcore.services.shared import has_any_role, Roles

def issue_allocation(name: str) -> dict:
    if not has_any_role((Roles.STOREKEEPER, Roles.SYS_ADMIN)):
        raise ServiceError(ErrorCode.FORBIDDEN, "Chỉ Thủ kho có quyền")
```

Centralize role guards in `services/shared/permissions.py` — do NOT duplicate `_require_X()` per module.

## 6. Test Standards

### Required tests per module
- Service-layer unit tests (validators, status transitions)
- Workflow smoke test (state machine reachability)
- API integration test (envelope shape, error codes)
- Permission gate test (role × action matrix)

### Test file location
- `assetcore/tests/test_imm<XX>.py` — one file per module
- `assetcore/tests/test_workflows.py` — cross-module workflow smoke

### Coverage target
- Services >50 LOC: 70%+ line coverage
- All state transitions: 100% transition coverage
- All ServiceError raises: at least 1 test asserting error code

## 8. Vietnamese vs English

- **User-facing labels**: Vietnamese (form labels, error messages, workflow action names)
- **Code identifiers**: English (function names, fieldname, doctype name in code)
- **Documentation**: Vietnamese for narrative; English for code blocks; technical terms can stay English (e.g., "scheduler", "workflow", "DocPerm")
- **Workflow state names**: English Title Case (used in JSON + code) — display label rendered separately
- **Status labels in Select fields**: English (`Open`, `Closed`) — UI translates if needed

## 10. Forbidden actions (CLAUDE.md §19 expanded)

- ❌ Modify ERPNext core JSON or Python files
- ❌ Hardcode role/status strings (use `Roles.X`, `Status.Y`)
- ❌ Skip audit trail logging
- ❌ Bypass workflow state machine to set state directly via `frappe.db.set_value("...", "workflow_state", ...)` — must go through `apply_workflow()` or service transition
- ❌ Build UI before BE/workflow exists
- ❌ Add `System Manager` role to a non-admin DocType
- ❌ Use unprefixed DocType name for new DocTypes
- ❌ Create CAPA without root-cause method
- ❌ Direct `frappe.db.sql()` from a service when a repository method would do
- ❌ Inline `try/except: pass` that swallows errors silently — log via `frappe.log_error`
- ❌ Dùng `doc.save()` để mutate workflow_state trên submitted document — phải dùng `frappe.db.set_value(DocType, name, "workflow_state", state, update_modified=False)` và nếu cần kèm `doc.reload()` để sync in-memory doc
- ❌ Tạo hai bộ function song song cùng tên (cũ + mới) trong cùng service file — khi refactor naming, xóa bộ cũ trước khi thêm bộ mới, tránh 1000-line file với duplicate logic

## 11. BE-FE Naming Contract (CRITICAL)

Khi build một module mới, function names phải nhất quán từ spec → BE → FE:

| Layer | Source | Rule |
|---|---|---|
| Spec | `docs/imm-XX/05_API_Specification.md` | Định nghĩa function name chính thức |
| BE API | `api/immXX.py` | Tên `@frappe.whitelist` function = tên trong spec |
| BE Service | `services/immXX.py` | Tên entrypoint = tên spec hoặc có thể thêm hậu tố `_by_name`, `_with_capa` nếu cần overload |
| FE API | `frontend/src/api/immXX.ts` | Gọi đúng tên: `assetcore.api.immXX.<spec_function_name>` |

**Verify checklist trước khi commit:**
- [ ] Mỗi `@frappe.whitelist` trong `api/immXX.py` có tên khớp với spec?
- [ ] Mỗi `frappeGet/frappePost` trong `api/immXX.ts` gọi đúng path `assetcore.api.immXX.<name>`?
- [ ] Không có duplicate function (cũ + mới) trong service file?
- [ ] Mỗi `doc.<field>` trong service có field tương ứng trong DocType JSON?
